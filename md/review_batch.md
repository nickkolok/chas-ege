# Ревью пачки пуллреквестов

Как проверять один PR — в [Как делать ревью пуллреквеста](how_to_review_PR.md).
Здесь — порядок работы, когда PR в задании несколько: что сделать один раз на всю пачку,
как отсеять лишнее и как найти связи между PR до того, как вникать в каждый.

Ниже `PRS` — номера PR пачки через пробел: `PRS="3705 3710 3711 3717 3720"`.

## 1. Подготовка — один раз на пачку

```bash
git fetch upstream
git fetch upstream '+refs/pull/*/head:refs/remotes/upstream/pr/*'   # головы всех PR, за секунды
```

Затем собрать актуальный `devel`, запомнить число тестов и сохранить сборку —
с ней сравниваются все PR пачки (подробно — в [ревью пуллреквеста](how_to_review_PR.md),
«Подготовка (один раз на сборку)» и «Проверка «байт в байт»»):

```bash
npm test 2>&1 | grep -E 'Не удалось|Всего тестов'   # число тестов devel — то, с чем сравнивать
mkdir -p /tmp/builds && cp -r build /tmp/builds/devel && ln -s "$PWD/node_modules" /tmp/builds/node_modules
```

Каждому PR — своя рабочая копия, слитая с `devel` локально
(«Несколько PR сразу: отдельный `git worktree` на каждый»).

PR в документацию (`md/`) вливаются в ветку `md-qwen-repo-structure`:
для них всюду вместо `upstream/devel` — `upstream/md-qwen-repo-structure`.

## 2. Отсев

```bash
for n in $PRS; do git merge-base --is-ancestor upstream/pr/$n upstream/devel && echo "$n смёржен"; done
```

PR вливаются merge-коммитом, поэтому голова смёрженного PR — предок `devel`.
Закрыт ли PR без мержа, по git не узнать: если в задании это не сказано,
прочитать страницы всех PR пачки за один раз.

Смёрженный или закрытый PR — одна строка в протоколе, дальше он не рассматривается.

## 3. Карта пачки — до чтения кода

Что меняет каждый PR (по папкам):

```bash
for n in $PRS; do echo "$n: $(git diff --name-only upstream/devel...upstream/pr/$n | cut -d/ -f1 | sort | uniq -c | tr -s ' ' | tr '\n' ' ')"; done
# 3717:  1 dev  2 lib  5 zdn
```

Файлы, которые меняют два PR и больше:

```bash
for n in $PRS; do git diff --name-only upstream/devel...upstream/pr/$n; done | sort | uniq -d
```

Конфликты — каждого PR с `devel` и всех пар между собой:

```bash
for a in $PRS; do
	git merge-tree --write-tree upstream/pr/$a upstream/devel >/dev/null || echo "$a и devel"
	for b in $PRS; do
		[ "$a" -lt "$b" ] || continue
		git merge-tree --write-tree upstream/pr/$a upstream/pr/$b >/dev/null ||
			echo "$a и $b: $(git merge-tree --write-tree --name-only upstream/pr/$a upstream/pr/$b | sed -n '2,/^$/p' | tr '\n' ' ')"
	done
done
# 3711 и 3717: lib/rectilinearSolid.js zdn/matege2024b/11/506579.js
```

Одинаковые правки в разных PR (один общий коммит) сливаются без конфликта,
а разные правки одного места — нет: такие пары сводятся до мержа.
Конфликт в `main.js` одной папки — обычно соседние строки двух новых шаблонов, он разрешается
тем, что остаются обе строки.

Одна и та же функция под разными именами — `git log -G` по головам PR
(«Искать ту же функцию в других открытых PR»).

Потребители изменённой функции — не только в `devel` и в пачке, но и в любых открытых PR:

```bash
git log --source --format='%S %h %s' -G 'selectVerbGender\(' --remotes='upstream/pr/*' --not upstream/devel -- zdn | sort -u
# upstream/pr/3526 0ec248881 [zdn][fix] 3488 - verb gender agreement with selectVerbGender
```

В выдачу попадают и давно закрытые PR — их состояние проверяется на странице PR.

## 4. Что проверять — по тому, что изменено

Тип бывает у PR, а не у пачки: библиотечный PR может менять шаблон, а шаблонный — библиотеку.
Проверки берутся по всем папкам, которые PR меняет.

| Изменено | Проверить |
|---|---|
| `lib/`, `src/` | собрать ветку, слитую с `devel`; тестов не меньше, чем в `devel`, и нет «Не удалось загрузить»; потребители из `devel` и из открытых PR — байт в байт или с объяснёнными отличиями |
| `zdn/` | массовый прогон на сборке ветки PR; ответы — своей формулой; диапазоны чисел — против группы прототипа ФИПИ; чертежи — листом картинок (`dev/contact-sheet.js`), а не по пяти примерам |
| `dev/` | правильные команды дают тот же вывод, что на `devel`, байт в байт |
| `md/` | команды и примеры из текста запущены |

Если PR меняет и `lib/`, и шаблон, примеры `chas-ege-taskbot` ничего не показывают,
даже когда задачи генерируются: бот берёт библиотеку из `devel`.

## 5. Протокол

- В начале — таблица: PR, состояние, вердикт (смёрженные и закрытые — одной строкой).
- По каждому PR: что проверено — с числами (сколько задач, сколько тестов, что совпало байт в байт);
  замечания — с пометкой «блокирует», «желательно» или «мелочь»; где понятно, как исправить, — готовый `suggestion`.
- Отдельно — связи между PR: конфликты, общие правки, порядок мержа.
- Утверждение о слиянии — только после `git merge-tree`, о чертеже — только после листа картинок.

Правки по итогам ревью присылаются через [`silentpr`](silentpr.md).
