# Как делать ревью пуллреквеста


## Убедиться, что проект скачан полностью

Либо с помощью `git clone`, либо, если это невозможно,
то [по этой инструкции](download_without_git.md).


## Не повторяться и не флудить

Ревьюеру не следует писать замечание,
если строчкой выше или ниже написан аналогичный комментарий
(от этого же или другого ревьюера).
Также не следует писать "Бамп!", "Не вижу ответа" и прочие "подгонялки".


## Опираться на факты

Если проводится ревью изменений в библиотеку,
не следует голословно утверждать, что какая-то функция упадёт с ошибкой
или выдаст неверный результат.
Необходимо приложить MWE (minimal working example),
который можно скопировать в консоль и пронаблюдать ошибку.

Если проводится ревью шаблона
и при этом в обсуждении приложены результаты работы этого шаблона
(т.е. сгенерированные задачи),
то не следует пытаться доказать, что шаблон никогда не сгенерирует задачу,
всегда будет падать с ошибкой, повиснет и т.д.
Вместо этого следует проверить правильность составленных задач
и ещё раз перечитать код шаблона.


## Локализовать Code Style

Например, если во всём файле пробелы вокруг знака `+` ставятся,
а в каком-то одном месте не ставятся,
то имеет смысл предложить это исправить.
Однако не следует настаивать на замене кавычек с двойных на одинарные
(или наоборот) во всё файле на основании того,
что где-то в другом файле ревьюеру встречались одинарные (или, наоборот, двойные).


## Искать непонятное

Встретив незнакомую или нестандартную функцию или другой идентификатор,
следует поискать другие упоминания этого идентификатора в проекте,
который, напомним, должен быть скачан полностью
(вероятно, искать с помощью утилиты `grep`).


## Искать ту же функцию в других открытых PR

Ревью PR в `lib/` стоит начать с вопроса, не добавляет ли то же самое другой открытый PR
(нередко того же автора и под другим именем). Головы всех PR скачиваются за секунды,
а `git log -G` находит коммиты вне `devel`, которые добавляют или удаляют строки по образцу:

```bash
git fetch upstream '+refs/pull/*/head:refs/remotes/upstream/pr/*'
git log --source --format='%S  %s' -G 'scalprod|scalarProduct|veclength' \
	--remotes='upstream/pr/*' --not upstream/devel -- lib src | sort -u
```

Искать стоит и по именам с синонимами, и по характерной строке реализации
(например, `-G 'drawLine\(xs\[i\]'`). В выдачу попадают и закрытые PR, их состояние
проверяется на GitHub. Пересекающиеся PR сводятся в один до мержа.

## Предлагать исправления

Если ревьюеру понятно, как можно исправить замечание,
то желательно оформить `suggestion`,
корректно прикрепив его к строке или диапазону строк и убедившись,
что оно не нарушает отступы.



## Ассистенты-ревьюеры

Главное, о чём нужно помнить:
во-первых, каждый ассистент-ревьюер имеет свою зону ответственности и обычно игнорирует то, что за её пределами;
во-вторых, ревьюеры (любые) могут ошибаться, хотя и нечасто, так что за ними надо перепроверять.

### `chas-ege-taskbot`

Просто генерирует примеры задач или констатирует, что задача не генерируется.
Комментарии не читает, в код не смотрит, общаться с ним бесполезно.

Если PR добавляет или меняет функции в `lib/`, а шаблон их вызывает,
ответ бота ничего не говорит о шаблоне: бот гоняет шаблон из PR не на сборке
ветки PR, и новой функции в его бандле нет. Так, в #3717 бот на каждом прогоне
писал «ЗАДАЧА_НЕ_ГЕНЕРИРУЕТСЯ», а на сборке самой ветки шаблон работал;
на бандле `devel` он падает с `ReferenceError: RectilinearSolid is not defined`.
`chas-ege-marta` в таком случае тоже нечего проверять.
Примеры для таких PR нужно получить самому на сборке ветки PR
(см. «Массовый прогон шаблона»).

### `chas-ege-marta`

Проверяет математическую и лингвистическую правильность последней пачки примеров,
которые составил `chas-ege-taskbot`.
Код не смотрит.

### `chas-ege-yuliya`

Смотрит на мелочи в коде:
опечатки в именах переменных и тексте,
пропущенные `;` и прочее такое вот.



## Массовый прогон шаблона

Пяти примеров из комментария бота мало: ошибка на краю диапазона, вырожденный чертёж
или неверный вариант `preference` в них может не попасть. Шаблон стоит прогнать
сотни раз и проверить **ответы своей формулой**, **диапазоны данных** и **чертежи**.

Считая частоты, помните: у `sl()` и `.iz()` вероятности крайних значений могут быть снижены.
Это известное явление, не требующее коррекции ([подробнее](random.md)): перекос частот — не ошибка шаблона.

Для этого есть `dev/run-node-template.js`: шаблон запускается в голом Node.js (jsdom),
без браузера. 300 генераций — меньше секунды, с чертежами — около 15 секунд.

### Подготовка (один раз на сборку)

```bash
git fetch upstream
git checkout upstream/devel
npm install
npm install --no-save grunt-cli canvas   # оба пакета — одной командой, см. «Подводные камни»
./node_modules/.bin/grunt
```

Сборка кладёт раннер в `build/dev/run-node-template.js`, а бандл — в `build/lib/`.
Собирать нужно **актуальный** `devel`. Со старой сборкой раннер падает с ошибкой вроде
`nabor.importFrom is not a function`.

### Прогон шаблона из пуллреквеста

Сборка остаётся от `devel`, шаблон берётся из ветки PR:

```bash
git fetch upstream pull/1234/head:pr-1234 --force
git show pr-1234:zdn/matoge2024/16/392118.js > /tmp/392118.js
node build/dev/run-node-template.js --filepath /tmp/392118.js --iterations 300 --json --seed 1 > /tmp/392118.json
```

Если PR меняет `lib/`, собирать нужно саму ветку PR (`git checkout pr-1234`, затем `grunt`).

Полезные ключи:
- `--iterations N` — сколько примеров; при `preference` — сколько на **каждую** комбинацию;
- `--seed S` — воспроизводимость: с тем же зерном получаются те же задачи;
- `--json` — машинный вывод в stdout (тайминги и ошибки идут в stderr);
- без `--json` — текст, ответ и LaTeX-блок, как у `sh/headless-debug.mjs`.

Код возврата 1 — хотя бы одна генерация упала (подробности в stderr).

### Что в JSON

Массив, по элементу на задачу:
- `label` — `Example i/N` или `Combination k/n [["…"]], Example i/N`, то есть вариант `preference`;
- `txt` — HTML текста задания: формулы в `$…$`, десятичная запятая как `{,}`,
  чертёж — `<img src="data:image/png;base64,…">`;
- `ver` — правильные ответы, `nev` — неправильные, `rsh` — решение;
- `preference` — **все** варианты, которые объявил шаблон (выбранный — в `label`).

### Проверка «байт в байт»: правка не меняет задания

Нужна, когда PR меняет `src/chas2/task.js`, `lib/` или шаблоны, но по замыслу задания
меняться не должны (code style, комментарии, рефакторинг, новые проверки настроек),
или должны измениться только у части шаблонов.
С одним и тем же зерном генерация детерминирована, включая чертежи
(`--seed` подменяет `Math.random`), поэтому вывод до правки и после можно сравнить побайтно.

Правила:
1. **Заранее** выписать, у каких шаблонов задания должны измениться, а у каких нет.
2. Каждый шаблон гонять **отдельным процессом**. Зерно задаётся один раз на процесс,
   и если в одном процессе идут несколько шаблонов, изменение одного сдвигает генератор
   для всех следующих: «изменятся» и те, которых правка не касалась.
3. Перед сравнением прогнать эталон дважды и убедиться, что прогоны совпадают.
4. После каждого переключения коммита — `grunt`: раннер берёт бандл из сборки.
   Чтобы не пересобирать при каждом переключении, сборку можно сохранить: `cp -r build /tmp/builds/devel`
   и один раз `ln -s "$PWD/node_modules" /tmp/builds/node_modules`, после чего
   `node /tmp/builds/devel/dev/run-node-template.js …` работает со своим бандлом.
5. Поле `template` в JSON повторяет `--filepath` дословно, поэтому правленую копию шаблона
   запускайте по тому же относительному пути из другого каталога — иначе «изменятся» все задачи.

```bash
# Список шаблонов — по одному пути на строку
ls zdn/matege2024p/8/*.js | grep -v -e '/main\.js$' -e '/fipi\.js$' > /tmp/templates.txt

# Каждый шаблон — отдельным процессом, с одним и тем же зерном
gen() {
	mkdir -p "$1"
	xargs -P 4 -I{} sh -c 'node build/dev/run-node-template.js --filepath {} --iterations 10 --seed 1 --json --quiet > "$0/$(echo {} | tr / _).json" 2>/dev/null' "$1" < /tmp/templates.txt
}

git checkout <до-правки> && ./node_modules/.bin/grunt && gen /tmp/before
git checkout <после-правки> && ./node_modules/.bin/grunt && gen /tmp/after
diff -rq /tmp/before /tmp/after   # пусто — задания не изменились
```

Как читать результат:
- Изменился шаблон, которого правка не должна была касаться, — разбираться.
- Ожидаемое изменение не обнаружилось — не всегда ошибка: правка может касаться
  редкой ветки (например, исключить значение, которое выпадает раз из четырёхсот),
  и в выборку она не попала. Такую ветку проверить отдельно.
- Если шаблон исчерпал попытки `retryWhileError`, задач в файле меньше. Изменение
  числа попыток меняет вывод только начиная с этого места; до него задачи совпадают.
- Если должен был измениться только текст, удобно сравнить по задачам ответы,
  рисунки и текст отдельно:

```bash
node -e '
const [a, b] = process.argv.slice(1).map(f => JSON.parse(require("fs").readFileSync(f, "utf8")));
const img = t => (t.match(/<img[^>]*>/g) || []).join();
a.forEach((x, i) => {
	const y = b[i] || {};
	console.log(i, "ответ:", JSON.stringify(x.ver) === JSON.stringify(y.ver) ? "=" : "≠",
		"рисунок:", img(x.txt) === img(y.txt) ? "=" : "≠",
		"текст:", x.txt.replace(/<img[^>]*>/g, "") === (y.txt || "").replace(/<img[^>]*>/g, "") ? "=" : "≠");
});' /tmp/before/zdn_….json /tmp/after/zdn_….json
```

### Подводные камни

- **`npm install --no-save` второй раз удаляет то, что поставил первый.** Пакеты,
  поставленные с `--no-save`, не записаны в `package.json`, и следующий `npm install`
  удаляет их как лишние (проверено на npm 10). Поэтому `grunt-cli` и `canvas` ставятся
  одной командой, а после любого `npm install` их нужно поставить заново.
- **Свой скрипт на jsdom сам не завершается.** Если скопировать окружение из
  `dev/run-node-template.js` (окно jsdom с бандлом), то после работы процесс не выходит:
  окно держит таймеры. Раннер завершается сам, потому что в конце вызывает `process.exit()`;
  в своём скрипте нужно сделать так же, иначе `node script.js | …` или ожидание в CI повиснет.
