# Как делать ревью пуллреквеста


## Убедиться, что проект скачан полностью

Либо с помощью `git clone`, либо, если это невозможно,
то [по этой инструкции](download_without_git.md).


## Не повторяться и не флудить

Ревьюеру не следует писать замечание,
если строчкой выше или ниже написан аналогичный комментарий
(от этого же или другого ревьюера).
Также не следует писать "Бамп!", "Не вижу ответа" и прочие "подгонялки".


## Опираться на факты

Если проводится ревью изменений в библиотеку,
не следует голословно утверждать, что какая-то функция упадёт с ошибкой
или выдаст неверный результат.
Необходимо приложить MWE (minimal working example),
который можно скопировать в консоль и пронаблюдать ошибку.

Если проводится ревью шаблона
и при этом в обсуждении приложены результаты работы этого шаблона
(т.е. сгенерированные задачи),
то не следует пытаться доказать, что шаблон никогда не сгенерирует задачу,
всегда будет падать с ошибкой, повиснет и т.д.
Вместо этого следует проверить правильность составленных задач
и ещё раз перечитать код шаблона.


## Локализовать Code Style

Например, если во всём файле пробелы вокруг знака `+` ставятся,
а в каком-то одном месте не ставятся,
то имеет смысл предложить это исправить.
Однако не следует настаивать на замене кавычек с двойных на одинарные
(или наоборот) во всё файле на основании того,
что где-то в другом файле ревьюеру встречались одинарные (или, наоборот, двойные).


## Искать непонятное

Встретив незнакомую или нестандартную функцию или другой идентификатор,
следует поискать другие упоминания этого идентификатора в проекте,
который, напомним, должен быть скачан полностью
(вероятно, искать с помощью утилиты `grep`).


## Предлагать исправления

Если ревьюеру понятно, как можно исправить замечание,
то желательно оформить `suggestion`,
корректно прикрепив его к строке или диапазону строк и убедившись,
что оно не нарушает отступы.



## Ассистенты-ревьюеры

Главное, о чём нужно помнить:
во-первых, каждый ассистент-ревьюер имеет свою зону ответственности и обычно игнорирует то, что за её пределами;
во-вторых, ревьюеры (любые) могут ошибаться, хотя и нечасто, так что за ними надо перепроверять.

### `chas-ege-taskbot`

Просто генерирует примеры задач или констатирует, что задача не генерируется.
Комментарии не читает, в код не смотрит, общаться с ним бесполезно.

### `chas-ege-marta`

Проверяет математическую и лингвистическую правильность последней пачки примеров,
которые составил `chas-ege-taskbot`.
Код не смотрит.

### `chas-ege-yuliya`

Смотрит на мелочи в коде:
опечатки в именах переменных и тексте,
пропущенные `;` и прочее такое вот.



## Массовый прогон шаблона

Пяти примеров из комментария бота мало: ошибка на краю диапазона, вырожденный чертёж
или неверный вариант `preference` в них может не попасть. Шаблон стоит прогнать
сотни раз и проверить **ответы своей формулой**, **диапазоны данных** и **чертежи**.

Для этого есть `dev/run-node-template.js`: шаблон запускается в голом Node.js (jsdom),
без браузера. 300 генераций — меньше секунды, с чертежами — около 15 секунд.

### Подготовка (один раз на сборку)

```bash
git fetch upstream
git checkout upstream/devel
npm install
npm install --no-save grunt-cli canvas   # оба пакета — одной командой, см. «Подводные камни»
./node_modules/.bin/grunt
```

Сборка кладёт раннер в `build/dev/run-node-template.js`, а бандл — в `build/lib/`.
Собирать нужно **актуальный** `devel`. Со старой сборкой раннер падает с ошибкой вроде
`nabor.importFrom is not a function`.

### Прогон шаблона из пуллреквеста

Сборка остаётся от `devel`, шаблон берётся из ветки PR:

```bash
git fetch upstream pull/1234/head:pr-1234 --force
git show pr-1234:zdn/matoge2024/16/392118.js > /tmp/392118.js
node build/dev/run-node-template.js --filepath /tmp/392118.js --iterations 300 --json --seed 1 > /tmp/392118.json
```

Если PR меняет `lib/`, собирать нужно саму ветку PR (`git checkout pr-1234`, затем `grunt`).

Полезные ключи:
- `--iterations N` — сколько примеров; при `preference` — сколько на **каждую** комбинацию;
- `--seed S` — воспроизводимость: с тем же зерном получаются те же задачи;
- `--json` — машинный вывод в stdout (тайминги и ошибки идут в stderr);
- без `--json` — текст, ответ и LaTeX-блок, как у `sh/headless-debug.mjs`.

Код возврата 1 — хотя бы одна генерация упала (подробности в stderr).

### Что в JSON

Массив, по элементу на задачу:
- `label` — `Example i/N` или `Combination k/n [["…"]], Example i/N`, то есть вариант `preference`;
- `txt` — HTML текста задания: формулы в `$…$`, десятичная запятая как `{,}`,
  чертёж — `<img src="data:image/png;base64,…">`;
- `ver` — правильные ответы, `nev` — неправильные, `rsh` — решение;
- `preference` — **все** варианты, которые объявил шаблон (выбранный — в `label`).
