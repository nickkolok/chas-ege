# Рекомендации и соглашения по работе с `git`

Это - НЕ инструкция для начинающих.
Здесь приводятся рекомендации, соглашения и нетривиальные советы
для тех, кто уже более-менее понимает, как работать с `git`.


## Основная ветка - `devel`

И да, мы отказались от `master` до того, как это стало `main`стримом.


## Удалённые репозитории

Не от слова "удалить", а от слова "далеко".

Предполагается, что основной репозиторий проекта называется `upstream`,
а остальные форки контрибьюторов - по их никам, т.е. как-то так:

```
$ git remote -v
upstream  git@github.com:nickkolok/chas-ege.git (fetch)
upstream  git@github.com:nickkolok/chas-ege.git (push)
kalendar2       git@github.com:Kalendar2/chas-ege.git (fetch)
kalendar2       git@github.com:Kalendar2/chas-ege.git (push)
sugarhedgehog   git@github.com:SugarHedgehog/chas-ege.git (fetch)
sugarhedgehog   git@github.com:SugarHedgehog/chas-ege.git (push)
zer00player     git@github.com:Zer00Player/chas-ege.git (fetch)
zer00player     git@github.com:Zer00Player/chas-ege.git (push)
```

(и, возможно, ещё что-нибудь).


## Начало доработки чужого пуллреквеста

Забираем ветку из PR 12345678 локально:

```
git checkout upstream/devel
git fetch upstream pull/12345678/head:pr-12345678 --force
git checkout pr-12345678
```


## Работа над новой фичей

```
git fetch upstream
git checkout upstream/devel
git checkout -b имя_ветки
```
Двумя командами, а не одной - по опыту нашей команды это безопаснее.


А в конце, понятно, `git push`.


## Добавление нового шаблона

Одним коммитом добавляется сам файл нового шаблона,
соответствующая строка в `main.js` и в `fipi.js`
(если `fipi.js` есть в соотв. папке и задача соответствует ФИПИ).
Если нужной категории нет, этим же коммитом создаётся `main.js`
с единственным номером:
```js
window.nomer=[
	1234567890,
].iz();
```
где `1234567890` - номер добавляемого шаблона.

Как правило, соответствующая ветка называется `newtask-1234567890`.


## Принцип атомарности

Каждое замечание по пуллреквесту,
а также самостоятельно найденная проблема,
исправляется отдельным коммитом с осмысленным названием.

Исправление code style всегда идёт отдельным коммитом.

Исправление орфографии и пунктуации всегда идёт отдельным коммитом.


## Соглашения об именовании коммитов и PR

| Префикс | Значение |
|---|---|
| `[zdn][new] <номер>` | Новая задача |
| `[zdn][fix]` | Исправление задачи |
| `[zdn][up]` | Обновление / расширение вариантов |
| `[zdn][ref]` | Рефакторинг задачи |
| `[zdn][main]` | Изменение main.js (частоты, номера) |
| `[zdn][sym]` | Симлинки |
| `[lib]` | Библиотеки |
| `[sh]` | Оболочки |
| `[css]` | Стили |
| `[ext]` | Внешние зависимости |
| `[CI]` | GitHub Actions |
| `[doc]` | Документация |
| `[script]` | Скрипты |
| `[code style]` | Косметика |
| `[core]` | Ядро |


## Команды, которых лучше избегать

### `git rebase`

Как правило, при доработке пуллреквестов использовать его - плохая идея,
если только в пуллреквесте или задании не сказано явно,
что нужно отребейзить.
Неуместный `git rebase` ломает историю обсуждения пуллреквеста.
Однако, `git rebase` может быть изредка полезен локально, если не сделан `git push`
(или хотя бы не открыт пуллреквест).


### `git push --force` / `git push --force-with-lease`

Про существование этой команды, честно говоря, вообще лучше не знать.
И не использовать её, если этого не требуется явно.


### `git add .` и `git add -A`

Может случайно включить в коммит что-нибудь, что лежало в репозитории без дела,
но и без вписания в `.gitignore`.
Лучше всегда указывать, какие конкретно файлы надо `git add`.


### `git pull`

Это команда хороша тем, что делает одновременно `fetch` и `merge`,
и ровно этим же плоха:
она частенько засоряет историю merge-коммитами,
превращая её в паутину.
В проекте не принято иметь большие ветки,
в которые надо было бы часто приливать внешние изменения.

## Соглашение о `silentpr`

Это, прямо скажем, экзотика.
Применяется из-за крайне кривого разграничения прав.
У нас не открывают пуллреквест в открытый пуллреквест.
Вместо этого, если `bob` открыл в апстрим пуллреквест из ветки `foo`,
а `charlie` хочет прислать туда правки,
то `charlie` создаёт у себя в форке ветку `silentpr/bob/foo`.
А дальше скрипты разберутся, переносить или не переносить и когда.
Иногда решение принимает автор пуллреквеста, иногда maintainer.

Имя пользователя переводится в нижний регистр, `Bob` становится `bob`.

Как узнать имя ветки PR: `git ls-remote https://github.com/<автор>/chas-ege` и найти строку с хешем головы PR.

При создании `silentpr`:

1. Разбивать изменения на коммиты по принципы атомарности.

2. Чем больше шанс изменений на то, чтобы быть принятыми,
тем раньше они должны быть закоммичены.
Первыми коммитится бесспорный code style (концевыми пробелы, например)
и очевидные опечатки,
и далее по возрастанию риска того, что коммит принят не будет.
Потому что `silentpr` может быть принят частично, до какого-то коммита.

3. Не следует мёржить ветку `devel` или библиотечные ветки в рамках `silentpr`
(если явно не требуется иное):
диффы `silentpr` часто просматриваются вручную.

4. В конце сообщения каждого коммита в `silentpr`
необходимо приводить ссылку на исходный пуллреквест:
```
Pull-Request-URL: https://...
```

### `silentpr` по шагам

В командах ниже `upstream` — основной репозиторий, `me` — remote своего форка
(свои форки здесь называют по нику, см. «Удалённые репозитории»).

**Головы всех пуллреквестов** скачиваются за секунды; дальше голова PR 1234 — `upstream/pr/1234`.
Скачивать заново перед каждой проверкой: головы меняются,
когда автор принимает `silentpr` или сливает `devel`.

```bash
git fetch upstream '+refs/pull/*/head:refs/remotes/upstream/pr/*'
```

**Автор и ветка пуллреквеста.** Если автор неизвестен, можно перебрать форки
и найти ветку с хешем головы PR:

```bash
N=3720
h=$(git rev-parse upstream/pr/$N)
for u in chas-ege-selena chas-ege-ulyana chas-ege-ellariya kira-dry-everywhere sugarhedgehog kalendar2 zer00player; do
	git ls-remote https://github.com/$u/chas-ege | grep "^$h" | grep refs/heads/ | sed "s|^|$u |"
done
# chas-ege-ulyana 24ba28dfa…	refs/heads/lib-selectverbgender-irregular
# chas-ege-ellariya 24ba28dfa…	refs/heads/silentpr/chas-ege-ulyana/lib-selectverbgender-irregular
```

Ветка PR — та, что не `silentpr/…`; вторая строка — уже принятый `silentpr`
на ту же голову. Список форков неполный: если ничего не нашлось,
автор и ветка — в шапке страницы PR («wants to merge … from автор:ветка»).
Ветка может содержать `/`, тогда и в имени `silentpr` она остаётся как есть:
`silentpr/chas-ege-ellariya/claude/genpifag-cache`.

**Подготовка.** `silentpr` строится от головы PR, а не от `devel`:

```bash
git checkout -B sp-3720 upstream/pr/3720
# … коммиты …
git push me sp-3720:refs/heads/silentpr/chas-ege-ulyana/lib-selectverbgender-irregular
```

- `Pull-Request-URL` идёт первым трейлером в конце сообщения, остальные трейлеры
  (`Co-Authored-By` и т. п.) — после него, без пустой строки между ними.
  Видит ли git трейлер: `git log -1 --format='%(trailers:key=Pull-Request-URL,valueonly)'`.
- Сливать с `devel` без явного указания нельзя (п. 3 выше), но проверять слияние — нужно: локально,
  без push. `git merge-tree --write-tree sp-3720 upstream/devel` печатает только хеш дерева
  и выходит с кодом 0, если конфликта нет; тесты и прогоны шаблонов — на локальном слиянии
  (см. [ревью пуллреквеста](how_to_review_PR.md), «Несколько PR сразу»).
- Одна и та же правка, нужная нескольким PR (общий коммит, скопированный в серию PR),
  переносится в каждый `silentpr` одним и тем же коммитом через `git cherry-pick`;
  меняется только `Pull-Request-URL`. Дифф одинаковый, поэтому после мержа одного PR
  остальные сольются без конфликта.
- Если в `silentpr` переносится чужой коммит (например, шаблон из PR, который закроют),
  `git cherry-pick` сохраняет автора и дату; откуда коммит и зачем перенесён —
  в сообщении.
- Новые коммиты к уже принятому `silentpr` кладутся поверх текущей головы PR,
  и push проходит как обычно. Если push отклонён, значит, в ветке есть непринятые
  коммиты, а PR ушёл вперёд: сначала разобраться (см. ниже), `--force` не использовать.

**Принят ли `silentpr`.** `silentpr` может быть принят частично, до какого-то коммита,
поэтому смотрят не на голову ветки, а на коммиты, которых ещё нет в PR:

```bash
git fetch upstream '+refs/pull/*/head:refs/remotes/upstream/pr/*'
git fetch me --prune
git log --oneline upstream/pr/3720..me/silentpr/chas-ege-ulyana/lib-selectverbgender-irregular
# пусто — принят целиком; иначе — ещё не принятые коммиты
```

Все `silentpr` своего форка сразу:

```bash
for b in $(git branch -r --list 'me/silentpr/*'); do
	echo "$b: не принято коммитов — $(git rev-list --count $b --not upstream/devel --remotes='upstream/pr/*')"
done
```

Смёржен ли сам PR: `git merge-base --is-ancestor upstream/pr/3720 upstream/devel && echo смёржен`
(PR вливаются merge-коммитом, поэтому голова смёрженного PR — предок `devel`).
Закрыт ли PR без мержа, по git не узнать: это видно только на странице PR.

**Удаление.** `silentpr` удаляют, когда он принят целиком или PR смёржен:

```bash
git push me --delete silentpr/bob/foo silentpr/bob/bar
```

Частично принятый `silentpr` не удаляют: непринятые коммиты ещё ждут решения.
Ветки, из которых открыты PR (не `silentpr`), не удаляют, пока PR открыт:
GitHub закроет PR вместе с веткой.

Иногда бывает, что ветку удалить нельзя: например, у ассистента в песочнице
push с удалением отклоняется (HTTP 403). В таком случае надо вывести команду удаления
тому, кто может её выполнить, — одной строкой, со всеми ветками,
в предположении, что если у исполняющего есть права на удаление веток,
то remote настроены (здесь снова `me` - свой ник):

```bash
git push me/chas-ege --delete silentpr/… silentpr/…
```
